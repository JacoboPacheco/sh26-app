Do not propose ideas of your own. Your job is to pressure-test theirs and turn it into a spec that can be built in the time left. CLAUDE.md → Idea already filled → that is the idea (its `Known risk` line, if any, is a spec constraint) and `$ARGUMENTS` is extra detail; Idea still a placeholder and `$ARGUMENTS` empty → stop and say: "no idea yet — type /ideas first."

**The lens for every question — what wins here.** ShellHacks judges on five equally weighted criteria: Completion (does it work), Originality (is it new or a twist), Design (how it looks and feels), Technology (what's under the hood and how well it's used), Practicality (could a real person use it). Judges grade what they see work in a few minutes — not code quality, not pitch polish. The last two years of winners share: a real problem a judge recognizes in one sentence; a live demo with one moment that makes a judge react; one genuinely technical piece (vision, AI, real-time; hardware is out for this starter) doing real work, not bolted on; polish on a small scope over breadth; a clear audience, often an underserved one; when going for a sponsor prize, the sponsor's tech used meaningfully. Push the spec toward one wow moment that works end to end, and cut whatever doesn't serve it. The demo is 3 minutes, one judge, at the table, on the laptop (localhost) plus a printed prop if the human has one — a phone only reaches the deployed URL: anything that needs setup time or a second person doesn't work.

0. If SPEC.md exists, or Current status's PHASE is 2 or higher: change nothing. Say "SPEC.md already exists (PHASE n) — /spec is kickoff-only; describe the feature and I'll append it to SPEC.md." and stop.
1. Read CLAUDE.md first, especially the sponsor/company challenges list and the stack. PHASE 0 → do PLAYBOOK Phase 0 first (its exit continues `/spec`). Sponsor list says `not released yet` → don't ask; SPEC.md's sponsor section says "list pending".
2. Interview the user with the AskUserQuestion tool, a few questions per round (CLAUDE.md → How to read me says how to ask). Skip anything obvious or already implied. If an answer is loose ("whatever works", "you pick"), propose a concrete interpretation and fold it into the next thing you show — the demo-script read-back is the confirmation; don't spend a round on it. Each round shows the draft demo script so far. Keep going until you can describe the demo screen by screen, usually two rounds; the whole skill is timeboxed to 20 minutes — if it's running long, write the spec with what you have and mark open questions in it. Dig into:
   - The one thing a judge must see in the demo for this to land
   - What data exists, where it comes from, and what happens with bad or missing input
   - Which sponsor challenges it realistically qualifies for. Rule: enter every *theme* track the idea already fits; for *API* tracks, the one whose tech is the heart of the idea plus at most ONE extra integration (built per PLAYBOOK Phase 3, so it can never break the demo). A bolted-on API loses "best use of" to a project where it's central, and every extra one costs hours and Completion. Never force a fit. Claim tests: a theme track needs the sentence "fits X because the judge watches Y" and the track's own wording must name the card's user or problem; an API track needs its free key obtainable at the event in 10 minutes; eligibility tracks (first-time hacker) go on anything eligible and never decide anything; never move a piece onto a sponsor's API when plain code does it more reliably — losing a track is cheaper than losing Completion.
   - What gets cut first if time runs short
   If the interview shows the skeleton can't make K+10, say so and offer the `RUNNER-UP` line from CLAUDE.md → Decisions in one AskUserQuestion before writing the spec (no such line → cut scope instead). Accepted → replace Idea and `# Project:` with it, delete the line, and restart the interview on it — the 20-minute timebox restarts too.
3. Write `SPEC.md`: problem (2 sentences), demo script (the exact clicks a judge sees), must-have features with an acceptance check for each, nice-to-haves in build order (last is cut first), explicitly out of scope, sponsor challenges targeted and why (naming the one extra integration, if any), new endpoints and tables, **starter pieces touched** (for each of `uploads.py`, `llm.py`, `seed.py`, `smoke_test.py`: reused as-is or needs extending — e.g. `complete(image=...)` for photos — and any extension goes in milestone 1), and the verification: which `smoke_test.py` checks get added and which committed sample file (e.g. `backend/demo/sample.jpg`) they use. Any latency or accuracy number in the spec is *measured after the skeleton*, never promised up front. Two defaults unless the idea truly needs otherwise: **no login screen** (CLAUDE.md → How this codebase is wired) and **milestone 1** per PLAYBOOK Phase 2.
